# UKey 现场字段探索任务单

更新时间：2026-09-03

执行环境：安装 CA/UKey 驱动、可登录江苏电力交易平台（JSPEC）的 Windows 电脑

代码基线：`main` 分支，至少包含提交 `4d08954`（支持读取同源 iframe、frame 和开放 Shadow DOM 中的可见表格）

## 1. 任务目标

在插有 UKey 的真实电脑上，对系统需要的 JSPEC 页面进行一次有清单的定向探索，形成完整、可复核的字段字典和页面操作记录。

本任务只负责确认真实页面结构和数据口径，不在证据不完整时猜测字段，不自动申报、下单、保存交易或绕过 UKey/CA 确认。探索结果将作为下一版采集器字段映射、跨页面合并和完整性校验的唯一依据。

## 2. 已确认事实

- JSPEC 业务表格可能位于门户页内嵌的同源 iframe/frame 中；旧采集器只检查顶层页面，因此曾出现“页面看得到、程序读不到”。
- 当前版本已经能够递归读取同源 iframe/frame 和开放 Shadow DOM 中的可见表格。
- 2026-09-02 现场截图证明，选择历史日期 `2026-08-24` 后，“用户日前出清”页面会返回 96 行数据，点击采集后系统提示“已采集 96 行”。
- “用户日前出清”已确认的真实表头为：`时间`、`出清电力`、`统一结算点电价临时结果`、`统一结算点电价最终结果`。
- 当前代码只保留该页面的时间和日前用户侧电价，遗漏了“出清电力”。这是字段建模遗漏，不是平台无法读取。
- 当前首页“96 点申报曲线对比”需要目标日缺省申报和历史实际负荷；仅采集用户日前出清价格，首页仍会显示等待真实数据。
- 当前系统以 `日期 + pointIndex（1～96）` 作为跨页面合并的基本键，但各页面真实日期口径、时间格式、单位和缺失值规则尚未全部现场确认。

## 3. 开始前准备

### 3.1 人员分工

- UKey 持有人：只负责插拔 UKey、完成登录、选择日期和确认页面，不向任何人提供 PIN、密码、Cookie、Token、证书或私钥。
- 现场探索人员：按本任务单逐页检查、记录和截图，不操作申报提交、交易确认、保存、删除、撤回等按钮。
- 开发人员：探索完成前不根据页面名称猜字段含义；收到证据后再实现字段映射和合并规则。

### 3.2 代码与运行环境

在另一台电脑的仓库目录执行：

```powershell
git switch main
git pull --ff-only origin main
git log -1 --oneline
```

确认最新提交包含本任务单和 `4d08954`。保留电脑上已有的未提交改动；若工作区不干净，不要覆盖、回滚或强制拉取，先记录 `git status -sb` 并暂停。

启动方式：

```powershell
.\run-system.ps1
```

若使用免安装交付包，则必须完整解压到新文件夹后双击 `启动系统.bat`，不要直接在压缩包内运行，也不要混用旧版本打开的 Chrome 数据窗口。

### 3.3 安全边界

- 不记录或截图 UKey PIN、密码、Cookie、Token、Authorization、证书内容、私钥、手机号等敏感信息。
- 不打开 Chrome 密码管理器、证书管理器或开发者工具的 Cookie/Storage 面板。
- 不点击任何“提交、确认申报、交易、保存、删除、撤回”按钮。
- 只读取页面上已经显示的数据；不得调用未公开接口、伪造请求或绕过平台权限。
- 截图若包含账号、单位或敏感业务数据，先脱敏；未经确认不得提交到公开 Git 仓库。

## 4. 每个页面必须记录的内容

每进入一个页面，都要完整记录以下项目。只记录“看见的事实”，没有看到就写“未确认”。

1. 左侧菜单的完整进入路径。
2. 页面加载完成后的完整 URL 和 hash 路由；URL 中若有票据或敏感参数，只记录去除敏感参数后的路径。
3. 页面标题、卡片标题和表格标题的原文。
4. 日期控件的标签、格式、默认日期、可选范围以及查询按钮文字。
5. 选择日期并查询后，页面是否刷新、局部刷新或打开新页。
6. 表格每一列表头的精确原文、左右顺序和单位；包括括号、空格、换行和“临时/最终”等后缀。
7. 每列至少三条脱敏样例值，并标记数据类型：日期、时间、整数、小数、文本、百分比、金额或空值。
8. 表格总行数；96 点页面必须核对首行、末行、时间间隔、是否包含 `24:00`、是否分页或虚拟滚动。
9. 空值的真实表现，例如 `-`、`--`、空白、`null`、`0`；确认临时值和最终值的优先关系。
10. 功率、电量和电价的单位，尤其区分 `MW`、`MWh`、`kWh`、`元/MWh` 和 `元`。
11. 页面是否位于 iframe/frame；若能安全查看 DOM，只记录 frame 层级和业务页 URL，不读取存储或凭证。
12. 是否有“导出”按钮；如果允许导出，只导出查询结果并记录文件名、工作表名、列名和行数。
13. 点击“采集并校验当日数据”后的完整中文提示、采集行数，以及系统哪个页面发生变化。
14. 同一页面至少选择两个可用日期复核：一个已知历史日期和另一个可用日期。若只能查到一个日期，记录平台限制。

### P0-3 已知表头的专门核验

“用户侧日前出清”必须逐项确认：

- `时间` 是否始终为 15 分钟粒度；
- `出清电力` 的单位是否为 MW，是否代表成交/出清而不是申报；
- `统一结算点电价临时结果` 的单位；
- `统一结算点电价最终结果` 的单位；
- 最终结果为 `-` 或空白时是否应回退到临时结果；
- 最终结果出现后临时结果是否仍保留；
- 查询不同历史日期时四列是否都会变化；
- 96 行是否完整，首点和末点分别是什么。

在含义确认前，不得把“出清电力”映射成“主动申报”或“缺省申报”。后续代码应使用独立字段，例如 `clearedPower`，最终名称以现场口径为准。

## 10. 完成标准

同时满足以下条件，才可以报告“现场探索完成”：

- P0-1 至 P0-8 全部有记录；无法访问的页面必须有明确原因和页面证据，不能留空。
- 每个96点页面都核对了真实表头、单位、首末时点、总行数、空值和至少两个可用日期。
- 明确区分主动申报、缺省申报、出清电力、实际负荷/电量，不互相代用。
- 明确临时价格和最终价格的优先规则。
- 明确每个首页必需字段来自哪个页面，并能用 `日期 + pointIndex` 对齐。
- 记录每个页面是否位于 iframe/frame、是否分页或虚拟滚动。
- 保留脱敏截图和允许获取的原始导出；没有读取或泄露任何凭证。
- 用当前版本执行一次采集，记录“程序实际保存字段”与“页面真实字段”的差异。
- 将第 7、8 节填写完整，列出仍需开发修复的差异清单。

## 11. 探索完成后的开发任务输入

现场探索结果交回后，下一版开发至少需要处理：

1. 为“出清电力”建立独立字段，贯通解析、白名单校验、历史存储和展示。
2. 按页面定义必需字段；字段不全时返回“部分采集”，不得仅因存在日期和点位就提示成功。
3. 将不同页面的数据按 `日期 + pointIndex` 合并，同时保留字段来源、采集时间和页面路由。
4. 分开展示“历史申报”“出清电力”“实际负荷”，禁止以错误业务名称展示数据。
5. 只有目标日缺省申报和所需历史实际负荷达到完整性门槛时，才生成96点申报建议。
6. 为每个真实表头增加回归测试，并增加“页面有96行但关键字段缺失”的失败测试。

本任务不直接授权修改生产数据、提交交易或部署生产系统。开发改造、重新打包和现场验收应作为后续独立任务执行。
