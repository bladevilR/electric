## ADDED Requirements

### Requirement: OTLP GenAI trace per actual request
The service MUST generate one complete OTLP document from each actual competition Agent request and MUST NOT create request evidence for an execution that did not occur.

#### Scenario: Successful Agent execution
- **WHEN** the Agent completes an HTTP or static-seed request
- **THEN** its trace contains a root span with a 32-character hexadecimal Trace ID, a unique 16-character hexadecimal Span ID, valid nanosecond timestamps, integer status code, `gen_ai.operation.name`, serialized input messages, and serialized output messages with `finish_reason`

#### Scenario: Domain tool execution
- **WHEN** the Agent reads and summarizes domain context
- **THEN** the trace contains child tool spans with matching Trace ID, correct parent Span ID, declared tool name, call ID, serialized arguments, serialized result, and status

#### Scenario: Exception handling
- **WHEN** capability routing or domain execution fails safely
- **THEN** the trace records the failure type and status on the failing span and records the Agent's non-fabricated recovery response

### Requirement: Trace storage integrity
Runtime trace storage SHALL append complete single-line OTLP JSON documents to an explicitly configured local file and SHALL fail closed when a trace document cannot be serialized or persisted.

#### Scenario: Concurrent sequential runner requests
- **WHEN** the official runner sends its three requests to one server process
- **THEN** all three complete trace documents are present without partial lines, duplicate span IDs, or cross-request parent references

#### Scenario: Corrupt runtime trace record
- **WHEN** export encounters malformed JSON or an invalid trace record
- **THEN** export fails and no formal submission directory is replaced

### Requirement: Static and dynamic export
The exporter SHALL merge runtime OTLP documents into one standard `resourceSpans` document while preserving complete trace boundaries and parent-child relationships.

#### Scenario: Static evidence export
- **WHEN** the static seed executes the primary analysis and memory evidence requests
- **THEN** `traces.json` contains all resulting traces and exactly one `invoke_agent` user instruction eligible for dynamic test generation

#### Scenario: Dynamic evidence export
- **WHEN** the official runner completes all three dynamic requests
- **THEN** `traces-dynamic.json` contains exactly the complete traces generated by that runner batch

### Requirement: Trace ID correlation
Every successful chat response MUST expose the same normalized Trace ID in response JSON and the W3C `traceparent` header, and final QA MUST correlate runner report IDs to dynamic trace IDs.

#### Scenario: Three-way dynamic correlation
- **WHEN** the runner reports three successful tests
- **THEN** each non-null report Trace ID appears exactly once as a trace in `traces-dynamic.json`, and no dynamic request trace is unaccounted for
