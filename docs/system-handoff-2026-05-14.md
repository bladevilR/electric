## 1. 一句话概况

本项目目前已经从“方案文档 + 原型页面 + JSPEC 抓取尝试”推进为一个可本地运行的电力交易 AI 辅助系统雏形。系统围绕本地标准化 96 点数据、企业后台式工作台、低价/高价观察建议、OpenAI-compatible 模型辅助分析、人工复核用交易草稿和本地追加式审计日志形成了初步闭环。

当前最需要接力的工作是把能量块成交结果、可买可卖限额、持仓量、实际负荷和结算文件补成可解析的数据资产，并接入后续的策略报告和人工复核页面。

## 3. 系统架构概览

### 3.1 总体结构

系统按“业务文件 / JSPEC 本地响应 / 人工导出 → 离线解析与标准化 → 本地数据文件 → 本地 API 服务 → 浏览器前端”的链路组织。

运行时定位为本机辅助系统，默认只绑定本机地址。系统使用本地文件作为主要数据交换介质，所有涉及 JSPEC 的后续数据补齐均应遵循人工导出和离线解析边界。

### 3.2 主应用模块

主应用目前大致包含以下模块域：

- 标准数据读取、压缩、汇总和浏览器数据生成。
- 确定性策略基线、低价/高价观察窗口和数据缺口识别。
- 策略报告 JSON/Markdown 生成。
- OpenAI-compatible 模型客户端。
- 交易台账、核对单、主体信息和标准数据缺口的集成摘要。
- 生产就绪、阻塞项和警告项检查。
- 预测负荷、持仓和交易限额等业务输入模板读取。
- 人工提案草稿生成和人工复核记录。
- 追加式 NDJSON 审计日志。
- UKey 助手状态、可见表格采集校验和字段映射。

前端目前为浅色企业后台样式，主要承担页面状态、模块渲染、API 调用和按钮事件组织。

### 3.3 前端页面

当前前端模块：

- 今日概览：交易日价格、数据准备度、AI 提醒。
- 收益情况：结算金额、价格区间、收益判断。
- 主体信息：交易主体与使用提醒。
- 结算复盘：现货核对单、缺项和结算指标。
- 复盘看板：96 点价格热力和点位明细。
- 市场数据：市场侧价格数据。
- 我的数据：申报、实际负荷、结算等用户侧数据。
- 数据准备情况：P0 源覆盖、字段完整性、缺口。
- 实时数据助手：打开本机浏览器、采集可见业务表格。
- AI 策略建议：低价/高价窗口、模型预测、阻塞原因。
- 交易草稿复核：生产就绪检查、草稿生成、人工复核记录。

### 3.4 API 能力范围

当前本地 API 覆盖以下能力域：

- 服务健康、路径和模型配置状态。
- 数据集、汇总信息和数据闭环台账。
- 生产就绪状态和控制项。
- 业务输入模板状态。
- UKey 助手状态、浏览器窗口控制和可见表格采集。
- 审计事件读取。
- 策略建议、策略报告和人工提案草稿生成。
- 人工复核记录。
- 本地数据刷新和集成摘要重建。

接口仅服务本地辅助分析，不承担自动交易、自动登录或自动申报职责。

## 4. 数据与实现状态

### 4.1 标准 96 点数据

JSPEC 标准化当前围绕本地 capture session、业务目标分类、日期和 96 点时间片合并、字段完整性检查、P0 源覆盖检查、空返回识别和质量报告生成展开。

标准化处理原则：

1. 只读取本地文件。
2. 按业务目标识别申报、出清、实时价格、实际负荷、结算等数据类型。
3. 将不同来源数据按日期和 96 点时间片合并。
4. 对字段完整性、P0 源覆盖、空返回和日期混杂写入质量报告。
5. 不补假值，不把空返回伪造成业务数据。

当前 2026-05-12 标准化结果：

- 行数：192。
- 日期：2026-05-12、2026-05-13。
- P0 源：`user_bid_96`、`user_default_bid_96`、`dayahead_user_clearing`、`dayahead_public_clearing`、`realtime_public_clearing`、`realtime_average_price`、`settle_day` 已有记录；`actual_load_96` 在标准质量报告中仍为缺口。
- 非空字段：`defaultDeclarationPower` 96 行，`realTimeAvgPrice` 57 行。
- 重要缺口：实际负荷为空、日结算为空、多日期混合、多个价格字段仍为 0 行，需要进一步确认字段映射或查询条件。

### 4.2 离线 inventory

当前已形成 2026-05-12 session 的本地响应索引、源 endpoint 摘要和标准输出检查。

2026-05-12 inventory 统计：

- 总响应：155。
- unsafe sensitive headers：0。
- 业务分类：bid 34、clearing 9、contract 15、listed 4、load 13、notice 5、settlement 15、unknown 60。

### 4.3 集成摘要

当前集成摘要读取交易结算一览表、现货核对单、JSPEC participant response 和标准数据 summary，形成本地闭环台账。

当前集成摘要已包含：

- 2026 年 1 月和 2 月交易台账数据。
- 2025-06、2025-09、2025-10、2025-11、2025-12、2026-01、2026-02 等现货核对单汇总。
- 市场主体：苏州市轨道交通集团有限公司。
- 标准数据字段完整性和缺口。

### 4.4 交易计算表解析

当前已解析 2026 年 1-5 月交易计算表，并形成申报电量、客户用电、小时交易、小时汇总和 ingest summary 等本地结果。

注意：部分交易计算表表头写的是“兆瓦时”，但日明细量级看起来更像 kWh。当前实现保留 raw value，没有自动换算。

### 4.5 人工导出数据

协议文档：`docs/jspec-safe-manual-export-protocol.md`

当前人工导出落盘区已建立以下目标目录和 manifest：

- 能量块成交结果。
- 能量块可买可卖量/限额。
- 持仓量查询。
- 合同分月电量。
- 用户实际 96 点日电量。
- 结算/下载中心文件。

当前这些 manifest 中 `files` 仍为空，说明还没有正式接入人工导出样本。

### 4.6 业务输入模板

当前业务输入模板覆盖：

- 预测负荷 96 点。
- 可买/可卖/合同/已成交持仓。
- 最小电量、最大草稿电量、买入限价、卖出底价等交易约束。

当前模板基本为空，因此提案草稿可以生成“观察型草稿”，但不能自动预填可靠的可交易电量和限价。

## 5. 数据补齐工作流

### 5.1 人工导出落盘

后续数据补齐建议按“页面查询 -> 导出文件 -> manifest 登记 -> parser 标准化 -> quality report”的链路推进。

优先落盘目录：

- `data/jspec/manual-exports/YYYY-MM-DD/energy_block_trades/`
- `data/jspec/manual-exports/YYYY-MM-DD/energy_block_limits/`
- `data/jspec/manual-exports/YYYY-MM-DD/position_curve/`
- `data/jspec/manual-exports/YYYY-MM-DD/actual_daily_96/`
- `data/jspec/manual-exports/YYYY-MM-DD/settlement_files/`

### 5.2 Parser 和事实表

每类数据需要形成独立 parser、标准表和质量报告：

- `energy_block_trades`：成交方向、执行日、小时、成交量、成交价、批次/序列。
- `energy_block_limits`：可买量、可卖量、限额、执行日、批次/序列。
- `position_curve`：持仓、已成交、可调买入、可调卖出、产品类型。
- `actual_daily_96`：用户实际 96 点用电量。
- `settlement_files`：结算文件索引、账期、文件类型、摘要字段。

### 5.3 UKey 助手后续方向

UKey 助手当前已经能表达本机浏览器状态和可见表格采集结果。下一步更有价值的是把可见表格字段映射、采集快照质量检查和导出文件 ingest 做成统一入口，减少人工搬运成本。

## 6. 运行状态口径

当前系统处于本地雏形阶段，已具备可运行的前端、后端、离线数据处理和审计记录能力，但运行表现与本地数据样本、环境变量、模型服务、Node/Python 环境、本地文件路径和人工导出文件状态有关。

需要特别注意：

- 当前主应用默认数据路径仍存在偏旧问题。
- 2026-05-12 数据已经形成 inventory 和标准化输出，但主应用默认不一定读取它。
- 当前人工导出样本尚未补齐。
- 当前业务输入模板基本为空。
- 当前策略输出应理解为 trial-only 的辅助观察，不构成可直接交易结论。

## 7. 质量与验证现状

当前项目已有 Node 原生测试和部分 JSPEC 工具测试，覆盖数据压缩、策略建议、策略报告、模型客户端边界、审计日志、业务输入读取、生产就绪检查、提案草稿、人工复核记录、本地 HTTP 服务合同、UKey 助手安全校验、96 点标准化、capture 脱敏、target 分类、离线 inventory、schema 文件和历史 replay 工具的单元行为。

这些测试可以说明当前实现已有基础回归保护，但不等于生产验收完成。后续任何环境迁移、默认数据切换、字段映射修正、业务样本补齐或交易约束扩展，都需要重新组织验证。

## 8. 当前已知问题

### 8.1 默认数据路径偏旧

当前部分默认路径仍指向 `session-20260507-101645`。2026-05-12 数据已经形成 inventory 和标准化输出，但主应用默认不一定读取它。

后续需要统一“当前稳定标准数据集”口径，并避免多处各自维护默认路径。

### 8.2 多个价格字段仍为 0 行

2026-05-12 标准报告显示多个日前/实时价格字段为 0 行，只有 `realTimeAvgPrice` 有 57 个非空点，`defaultDeclarationPower` 有 96 个非空点。

该问题需要结合原始响应字段、账号数据状态、日期条件、查询条件和接口语义继续判断。

### 8.3 实际负荷和日结算仍不足

`actual_load_96`、`settle_day` 在质量报告中仍是关键缺口。没有实际负荷和结算明细时，系统只能做价格观察和策略辅助，不能做完整收益归因和偏差考核结论。

### 8.4 能量块、限额、持仓尚未接入真实样本

schema 和人工导出 manifest 已有，但 `energy_block_trades`、`energy_block_limits`、`position_curve` 还没有实际文件。缺这些数据时，系统不应输出“可以买多少/可以卖多少”的确定性结论。

### 8.5 文档体系仍有分工重叠

现有 README 更面向终端试用用户，本文档更偏当前状态说明。生产运行、开发说明和业务操作说明之间仍需要进一步梳理分工。

### 8.6 根目录仍包含大量业务原件和历史资产

根目录包含 Excel、PDF、PPT、图片、音频、HTML 原型等。`.gitignore` 已忽略大多数二进制和原始业务文件，但长期工程化建议把“代码仓库”和“业务资料库”边界拆清。

## 9. 后续建设方向

后续建设不宜简单理解为“继续补几个接口”或“把现有脚本跑完”。当前系统已经涉及业务数据理解、96 点标准化、人工导出协议、交易台账集成、策略建议生成、审计留痕和模型辅助分析，后续推进需要重新评估数据来源、业务目标、工程架构和验收标准。

可继续研判的方向包括：

- 当前本地系统收口和默认数据口径统一。
- 离线数据工程和人工导出 parser。
- 合同、行情、通知、结算等标准表建设。
- 决策输入层和数据缺口报告。
- 可买/可卖边界、持仓敞口和人工复核候选建议。
- 数据库化、权限、角色、审计查询、任务调度和数据版本管理。
- 脱敏样本、CI 测试数据集和生产化验证。
- 负荷预测、价格窗口预测、回测、收益归因和约束优化。

以上方向之间存在依赖关系，不能脱离真实业务样本单独推进。

## 10. 接手关注点

接手时建议优先确认以下事项：

- 当前系统实际运行使用的是哪一份标准数据。
- 当前数据缺口是否影响业务判断。
- 人工导出协议是否仍被执行。
- UKey 助手是否能稳定读取可见表格并形成可用快照。
- 当前策略输出是否仍明确标注 trial-only 和人工确认。
- 审计日志是否仍能记录提案和人工复核。
- 业务原件、脱敏样本和代码仓库之间的边界是否清楚。

在上述事项未确认前，不建议把系统理解为生产交易系统。

## 11. 验收口径

当前阶段不要用“自动抓到了更多接口”作为成功标准。更合理的验收口径是：

- 系统能稳定本地启动。
- 页面能展示当前标准数据和数据缺口。
- 策略建议明确标注 trial-only 和人工确认。
- 交易草稿不会产生自动订单。
- 审计日志能记录提案和人工复核。
- JSPEC 数据只通过本地文件和人工导出进入系统。
- 敏感凭据不会进入仓库。
- 后续维护者能基于当前状态继续评估和补齐数据工程链路。
