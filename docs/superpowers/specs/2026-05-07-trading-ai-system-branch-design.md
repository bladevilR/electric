# 苏州地铁电力交易 AI 辅助策略系统分支设计说明

日期：2026-05-07  
状态：分支实现前设计稿  
目标读者：新建工作分支后的实现者、产品/业务确认人员、后续维护者

## 1. 先说清楚：我们到底要做什么

本项目不是再做一个静态看板，也不是简单仿一个网页皮肤。目标是一套面向苏州地铁电力采购与现货交易业务的决策辅助系统。

系统定位：

- 辅助交易人员做月度分配、D-2/D-3 能量块、D-1 日前申报、D 日实时风控。
- 接入 JSPEC 平台和内部 Excel/核对单数据，形成统一数据底座。
- 通过预测、规则、约束优化和复盘，给出可解释的策略建议。
- 不自动下单，不绕过 CA/UKey，不保存长期认证凭据，不承诺“自动炒电赚钱”。

第一阶段要落地的是“可运行的本地工程系统”：

- 有仿参考系统的企业后台界面。
- 有本地 API 服务。
- 有 JSPEC 标准数据接口。
- 有数据质量报告和缺口提示。
- 有策略建议的确定性基线算法。
- 有后续接数据库、任务调度、模型服务的清晰扩展点。

## 2. 来龙去脉

### 2.1 业务起点

已有文档判断很明确：苏州地铁电力交易规模足够大，1 分/度就是百万级年收益空间。当前业务不是从零开始，而是在已有人工经验、台账分析、现货核对和交易代理服务基础上进一步数据化、系统化。

业务优先级来自现有方案中的共识：

1. 年度/月度合同分配优化是最大静态盘子。
2. D-1 日前申报优化是第一阶段最重要的动态收益来源。
3. D-2/D-3 能量块调仓是真实存在的补充抓手。
4. D 日实时层先做风险提示和偏差控制，不作为一期主要收益承诺。

### 2.2 JSPEC 打通过程

JSPEC 页面需要 CA/UKey 登录。经过验证，合理采集方式不是绕过登录，而是在用户正常登录后，通过 Chrome 调试端口被动读取浏览器已经请求到的 XHR/fetch 响应。

当前已经完成：

- 能慢速打开/触发 P0 目标页面。
- 能捕获并脱敏 JSPEC 响应。
- 能把捕获响应整理成标准 96 点数据。
- 能输出 `standard-96.json`、`standard-96.csv`、`quality-report.md`。

当前 JSPEC 标准数据状态：

- 标准行数：192。
- 覆盖日期：2026-05-07、2026-05-08。
- P0 源覆盖：8/8。
- 缺省申报功率：96 个有效点。
- 实时均价：57 个有效点。
- 实际日电量：接口结构已拿到，但当前返回空列表。
- 日结算：接口已拿到，但当前返回 total = 0。

结论：数据链路已经打通，但训练模型和完整收益归因还缺历史 96 点负荷、日结算明细、现货核对单结构化结果。

### 2.3 UI 方向修正

一开始生成的是一个“本地看板”，但这不符合最终目标。用户明确指出参考 PDF 第 9 页中间几张截图来自同一套系统，真正要模仿的是那种企业后台系统，而不是 PPT 页面本身。

因此 UI 方向修正为：

- 浅色企业后台。
- 左侧浅蓝菜单。
- 顶部模块栏和筛选区。
- 白底卡片、蓝色按钮、表格、折线图、柱状图、状态标签。
- 页面像业务系统截图，而不是大屏驾驶舱。

当前已有 `trading-ai-system` 原型已朝该方向起壳，但后续实现应以本设计为准。

## 5. 目标系统产品设计

### 5.1 用户角色

交易决策人员：

- 看次日风险、价格窗口、申报建议、执行清单。

电力管理人员：

- 看月度结构、现货核对、结算偏差、合同覆盖。

管理层：

- 看收益、风险、执行率、节约金额、项目价值。

技术/数据人员：

- 看数据源状态、接口质量、任务日志、模型效果。

### 5.2 一级模块

数据中心：

- 公共数据：日前公开出清、实时公开出清、实时加权均价、系统负荷、新能源、天气。
- 私有数据：申报曲线、实际负荷、结算明细、核对单、合同、持仓。
- 数据质量：缺失率、日期错位、96 点完整性、异常值。

交易员工作台：

- 今日看法。
- 关键风险窗口。
- 推荐动作。
- 策略执行单。
- 人工确认状态。

策略中心：

- 月度分配策略。
- D-2/D-3 能量块策略。
- D-1 日前申报策略。
- D 日实时风险提示。
- 保守/平衡/进取三档方案。

预测中心：

- 96 点负荷预测。
- 96 点价格区间预测。
- 高价/低价窗口识别。
- 预测误差评估。

结算复盘：

- 日结算。
- 月结算。
- 现货核对单解析。
- 人工策略 vs 系统策略 vs 实际结果。
- 收益归因。

系统管理：

- 数据源配置。
- 采集任务。
- 规则版本。
- 用户与权限。
- 操作日志。

### 5.3 页面风格

## 6. 业务流程设计

月度流程：

1. 导入年度/月度合同和历史用电。
2. 生成月度负荷和价格趋势判断。
3. 给出月度合同覆盖建议。
4. 管理层确认。
5. 进入后续复盘。

D-2/D-3 流程：

1. 读取当前持仓和能量块窗口。
2. 识别分时段价格风险。
3. 输出买入/卖出/不动建议。
4. 人工确认。
5. 留痕复盘。

D-1 流程：

1. 读取 JSPEC 日前申报、日前出清、预测负荷、预测价格。
2. 生成 96 点申报建议。
3. 输出高价窗口、低价窗口、风险说明。
4. 人工确认并在 JSPEC 手动操作。
5. 系统记录人工采纳结果。

D 日流程：

1. 读取实时均价、实时出清、实际负荷。
2. 识别偏差和异常价格。
3. 发出风险提醒。
4. 人工处理。
5. 进入复盘台账。

复盘流程：

1. 导入结算明细和核对单。
2. 对比系统建议、人工执行、实际结果。
3. 计算收益/避损。
4. 标注失败原因。
5. 反馈给预测和策略规则。

### 7.2 数据源优先级

P0：

- JSPEC 96 点申报。
- JSPEC 日前/实时价格。
- JSPEC 实际日电量。
- JSPEC 日结算。
- 现货核对单 Excel。

P1：

- 月度交易台账。
- 合同/持仓。
- 历史 96 点负荷。
- 天气、客流、行车图、节假日。

P2：

- 系统负荷预测、新能源预测、检修计划。
- 规则版本库。
- 外部价格/政策公告。

### 7.3 数据质量规则

96 点完整性：

- 每个交易日每类 96 点数据应有 96 行。
- 时间点应从 00:15 到 24:00。
- 同一日期同一时间点不得重复。

日期对齐：

- 日前数据可能是 D+1。
- 实时数据通常是 D。
- 策略计算必须显式处理交易日与自然日错位。

缺口处理：

- 缺实际负荷时，不做偏差考核结论。
- 缺日结算时，不做最终收益归因。
- 缺价格时，只做数据缺口提示，不生成交易建议。

安全处理：

- 不保存 `x-ticket`、cookie、authorization。
- 不保存密码、验证码、CA/UKey 私钥信息。
- 不自动提交 JSPEC 业务动作。

## 8. 技术架构设计

### 8.1 推荐工程结构

建议新仓库结构：

```text
electric-trading-ai-system/
  apps/
    web/                  # 前端系统
    local-api/            # 本地 API 服务
  packages/
    jspec-capture/         # JSPEC 被动采集工具，可从现目录迁入
    data-core/             # 标准化、质量校验、Excel 解析
    strategy-core/         # 确定性策略和后续模型接口
  data/
    samples/               # 脱敏样本
    local/                 # 本地运行数据，不进 Git
  docs/
    references/            # 业务和视觉参考说明
    specs/                 # 设计文档
    plans/                 # 实施计划
```

如果短期不想迁移，也可以继续使用：

```text
E:\electric\trading-ai-system
E:\electric\jspec-capture
E:\electric\docs
```

但需要把抓包输出、浏览器 profile、Excel 原件加入忽略清单。

### 8.2 第一阶段技术选择

前端：

- 可以先继续用 Vanilla HTML/CSS/JS 快速迭代。
- 若进入长期开发，建议升级到 Vite + React 或 Vue + Element Plus，因为参考系统很像 Element UI 企业后台。

后端：

- 第一阶段用 Node 原生 HTTP 或轻量 Express/Fastify。
- 提供 `/api/dataset`、`/api/summary`、`/api/strategy`、`/api/refresh`。
- 本地文件数据先行，后续替换为 SQLite/PostgreSQL。

数据：

- 当前以 `standard-96.json` 为中心。
- 第二步接 Excel 解析。
- 第三步落 SQLite。

策略：

- 先做确定性规则基线。
- 再做统计预测。
- 最后接优化求解和模型服务。
